## 一、Agent 基础概念

### Q1: 什么是 Agent？和传统 LLM 调用有什么区别？

**面试官心理：** 考察你对 Agent 核心理念的理解，不是背概念。

**参考回答：**

> "我理解 Agent 的核心区别在于**自主行动能力**。
>
> 传统 LLM 调用是这样的：用户问一个问题，LLM 直接生成回答，**一次交互就结束了**。
>
> ```
> User → LLM → Answer
> ```
>
> 而 Agent 是：**感知→规划→行动→观察→迭代**的循环。
>
> ```
> 感知 → 规划 → 行动 → 观察 → [迭代] → 结束
>   ↑__________________|_______________|
> ```
>
> 我在 GopherSentinel 里就体现了这一点：
> - 用户问'帮我分析订单服务 CPU 飙高的问题'
> - Agent **感知**：解析出需要查日志、查指标、查文档
> - **规划**：制定执行计划，先并行查日志和指标，再综合分析
> - **行动**：调用 Prometheus 和 Loki 工具
> - **观察**：根据返回结果判断是否需要进一步查询
> - **迭代**：如果结果不够，再查相关文档补充
>
> 关键区别：**Agent 能调用外部工具，能根据结果调整策略**，而不仅是生成文本。"

### Q2: 什么是 ReAct 模式？为什么需要它？

**面试官心理：** 考察对 Agent 决策链的理解深度。

**参考回答：**

> "ReAct 是 **Reason + Act** 的结合，即**边推理边行动**。
>
> 我先说为什么需要它：
>
> 早期 Agent 有两种极端：
> 1. **纯推理**：LLM 在脑子里想，想完直接输出，结果容易'幻觉'和'空想'
> 2. **纯行动**：LLM 看到问题就调用工具，不管上下文，经常'乱调用'
>
> ReAct 的思路是：**Thought → Action → Observation** 三步循环。
>
> ```
> Thought: 我需要查 CPU 指标，用户说服务 A
> Action: 调用 prometheus.query(metric="cpu", service="A")
> Observation: 返回 CPU=87%
> Thought: 87% 确实很高，我需要查原因
> Action: 调用 loki.query("error", service="A")
> ...
> ```
>
> 我在项目中实现 ReAct 时，有几个关键设计：
>
> **1. Thought 的结构化**
> ```go
> type Thought struct {
>     Reasoning  string    // 推理过程
>     Action     string    // 下一步行动
>     Confidence float64   // 置信度 < 0.7 时触发重试
> }
> ```
>
> **2. 防止死循环**
> - 最大循环次数：10 次
> - 单次 Action 超时：30s
> - 整体任务超时：120s
>
> **3. 反思机制**
> ```go
> // 如果 Action 执行失败，触发反思
> if err != nil {
>     thought = "执行失败，原因是" + err.Error() + "，换一个思路试试"
>     continue  // 继续循环，而不是直接失败
> }
> ```
>
> 这样即使中间步骤出错，Agent 也能自我修正，而不是直接输出错误结果。"

## 二、RAG 系统设计

### Q3: 讲讲你的 RAG 链路是怎么设计的？

**面试官心理：** 这是必问题，考察 RAG 完整理解，而不是只会调 API。

**参考回答：**

> "我的 RAG 链路分 5 个阶段，不是简单的'查向量→返回'：
>
> ```
> 用户问题 → 查询改写 → 混合检索 → Rerank → 生成
> ```
>
> **第一阶段：查询改写（Query Rewrite）**
>
> 用户问题往往表述模糊，比如'服务 A 昨天有问题'，向量检索效果很差。
>
> 我做了查询扩展：
> ```go
> // 原问题: "服务A昨天有问题"
> // 改写后: "服务A 问题 故障 错误 2024-01-15"
> rewritten := llm.Generate(ctx, Prompt{
>     Template: `把用户问题改写成更适合检索的形式，
>               补充同义词和时间信息：
>               问题: {{.Query}}
>               改写:`,
>         Data: req.Query,
> })
> ```
>
> **第二阶段：混合检索（Hybrid Search）**
>
> 为什么混合？因为向量检索和关键词检索各有优势：
>
> | 检索方式 | 优势 | 劣势 |
> |---------|------|------|
> | 向量检索 | 语义相似、拼写容错 | 对专有名词不敏感 |
> | BM25 | 关键词精确匹配 | 语义泛化能力差 |
>
> 我用 **RRF (Reciprocal Rank Fusion)** 融合：
> ```go
> func RRF(hybridScore float64) float64 {
>     return 0.7*vectorScore + 0.3*bm25Score  // 权重可调
> }
> ```
>
> **第三阶段：Rerank（精排）**
>
> 混合检索召回 20 条，Rerank 精选 5 条。
>
> 选 BGE-Reranker 是因为：
> 1. 支持中文
> 2. 比向量检索更精准（用 Cross-Encoder 计算相关性）
> 3. 开源可本地部署，成本可控
>
> **第四阶段：上下文压缩**
>
> 直接把所有召回文档塞给 LLM 太费 Token，我用 LLMLingua 压缩：
> ```go
> compressed := compress(ctx, docs, maxTokens=4000)
> ```
>
> **第五阶段：生成 + 引用**
>
> 生成时带上引用来源，用户可以点进去看原文：
> ```
> 根据[文档1]和[文档3]，订单服务使用了连接池...
> ```
>
> ---
>
> 这套链路的效果：RAGAS Faithfulness 得分 0.87，原来纯向量检索只有 0.62。"

### Q4: RAG 召回效果不好怎么排查和优化？

**面试官心理：** 考察实战经验，不是纸上谈兵。

**参考回答：**

> "这是我在项目中踩过的坑，分两个维度说：
>
> **排查维度：先定位是哪个环节出问题**
>
> ```go
> // 我做的诊断工具
> func DiagnoseRAG(query string) *DiagnosisReport {
>     // 1. 检查 Embedding 质量
>     emb := embed(query)
>     if isAllZeros(emb) { return "Embedding 模型异常" }
>
>     // 2. 检查向量库是否有相关内容
>     results := vectorDB.Search(emb, topK=20)
>     if len(results) == 0 { return "向量库无相关内容" }
>     if avgScore(results) < 0.5 { return "召回分数过低" }
>
>     // 3. 检查 Rerank 后顺序是否合理
>     reranked := reranker.Rerank(query, results)
>     if topScore < 0.3 { return "Rerank 后top结果不相关" }
>
>     // 4. 检查 LLM 是否正确理解召回内容
>     llmResp := llm.Generate(ctx, query, docs)
>     if hasHallucination(llmResp) { return "LLM 幻觉" }
>
>     return "RAG链路正常"
> }
> ```
>
> **常见问题和解决方案：**
>
> **问题1：分块策略不对**
>
> - 症状：答案支离破碎，缺少上下文
> - 我踩的坑：最初按固定 500 token 分块，导致很多段落被切断
> - 解决：改用**语义分块**，按段落 + 滑动窗口 overlap
>
> **问题2：Embedding 模型不合适**
>
> - 症状：中文语义检索效果差
> - 我踩的坑：用了英文优化的模型（text-embedding-ada-002）
> - 解决：换成支持中文的模型（text-embedding-3-small / nomic-embed-text）
>
> **问题3：元数据过滤缺失**
>
> - 症状：召回的内容时间不对、服务不对
> - 解决：增加 metadata filter，`service='订单服务' AND time>'2024-01-01'`
>
> **问题4：Embedding 饱和**
>
> - 症状：不管问什么，Top 结果都是那几个文档
> - 解决：检查向量分布，做 Embedding 重新训练或微调
>
> ---
>
> 我的优化心得：**用数据驱动**。
>
> - 建了 100 条标注测试集
> - 每次改动后跑一遍，监控 Recall@5/10 指标
> - 记录 bad case，定期分析根因"

### Q5: 为什么要用 Rerank？直接用向量检索不行吗？

**面试官心理：** 考察对检索技术的深度理解，不是会用就行。

**参考回答：**

> "这个问题我当初也有疑惑，做完对比实验才理解。
>
> **向量检索 vs Rerank 的本质区别：**
>
> | 维度 | 向量检索 (Bi-Encoder) | Rerank (Cross-Encoder) |
> |-----|----------------------|----------------------|
> | 计算方式 | query 和 doc 分别编码，再算相似度 | query 和 doc **一起**过模型 |
> | 计算量 | O(n) 快速召回 | O(n×m) 但更精准 |
> | 精度 | 中等 | 高 |
> | 适用场景 | 粗召回 (Top 100→20) | 精排序 (Top 20→5) |
>
> **打个比方：**
> - 向量检索像是**海选**：快速从 10000 人里选出 100 人
> - Rerank 像是**面试**：仔细对比每个人和岗位的匹配度，选出 5 人
>
> **我的实验数据：**
>
> ```
> 纯向量检索 Top5 准确率:  62%
> + Rerank 后 Top5 准确率: 87%  ← 提升 25%
>
> 纯向量检索 Top20 准确率:  78%
> + Rerank 后 Top20 准确率: 91%
> ```
>
> **为什么提升这么大？**
>
> 举个例子：用户问'K8s 部署配置'
>
> 向量检索可能召回：
> 1. K8s 架构介绍  (向量相似度 0.85)
> 2. K8s 部署最佳实践 ← 正确答案
> 3. Docker 使用指南
> 4. K8s 运维手册
> 5. CI/CD 流程
>
> 因为'部署'在向量空间里和多个文档都接近，所以会召回噪音。
>
> Rerank 会综合考虑 query 和 doc 的交互关系，把真正讲部署配置的排在前面。
>
> **工程取舍：**
>
> Rerank 有代价：
> 1. 延迟增加 ~100ms（Cross-Encoder 比 Bi-Encoder 慢）
> 2. 需要额外部署 Rerank 模型
>
> 所以我的方案是：**两阶段召回**
> - 阶段1：向量检索快速召回 Top 20
> - 阶段2：Rerank 精选 Top 5
>
> 兼顾速度和精度。"

## 三、Multi-Agent 架构

### Q6: 讲讲你的 Multi-Agent 架构是怎么设计的？

**面试官心理：** 考察架构设计能力，Agent 之间怎么协作是关键。

**参考回答：**

> "我的设计参考了 **Supervisor Pattern + Map-Reduce** 的思想：
>
> ```
>                    ┌─────────────┐
>                    │   Master    │
>                    │  (Supervisor)│
>                    │  意图识别    │
>                    │  任务分发    │
>                    └──────┬──────┘
>                           │
>           ┌───────────────┼───────────────┐
>           │               │               │
>           ▼               ▼               ▼
>     ┌──────────┐   ┌──────────┐   ┌──────────┐
>     │  Log     │   │  Metric  │   │   Doc    │
>     │  Agent   │   │  Agent   │   │  Agent   │
>     │ (并行)   │   │ (并行)   │   │ (并行)   │
>     └────┬─────┘   └────┬─────┘   └────┬─────┘
>           │               │               │
>           └───────────────┼───────────────┘
>                           │
>                           ▼
>                    ┌─────────────┐
>                    │  Aggregator │
>                    │  (结果汇总)  │
>                    └─────────────┘
> ```
>
> **核心设计：Master-Worker 模型**
>
> ```go
> type MasterAgent struct {
>     workers    map[string]WorkerAgent
>     recognizer *IntentRecognizer
>     aggregator *ResultAggregator
> }
>
> // Master 的工作流程
> func (m *MasterAgent) Handle(ctx context.Context, query string) (string, error) {
>     // 1. 意图识别 - 判断需要哪些 Agent
>     intent := m.recognizer.Recognize(ctx, query)
>
>     if len(intent.Agents) == 0 {
>         return m.simpleRAG(query)  // 简单问题直接 RAG
>     }
>
>     // 2. 并行分发任务
>     results := m.dispatchParallel(ctx, intent.Agents, query)
>
>     // 3. 汇总结果
>     return m.aggregator.Merge(ctx, results)
> }
>
> // 并行调度 - 体现 Go 优势
> func (m *MasterAgent) dispatchParallel(ctx context.Context,
>     agents []string, query string) []*AgentResult {
>
>     var wg sync.WaitGroup
>     results := make(chan *AgentResult, len(agents))
>
>     for _, agentName := range agents {
>         wg.Add(1)
>         go func(name string) {
>             defer wg.Done()
>             result, _ := m.executeWithTimeout(ctx, name, query, 30*time.Second)
>             results <- result
>         }(agentName)
>     }
>
>     wg.Wait()
>     close(results)
>
>     return collectResults(results)
> }
> ```
>
> **为什么用 Go 而不是 Python？**
>
> 1. **Goroutine 极轻量**：同时调度 5 个 Agent，每个 Agent 栈只有 2KB
> 2. **并发原语丰富**：sync.WaitGroup、context、chan 用起来很优雅
> 3. **性能敏感**：RAG 链路中大量 JSON 序列化，Go 的性能优势明显
>
> **意图识别的实现：**
>
> ```go
> // 我用 few-shot prompting 做分类
> type Intent struct {
>     Agents     []string           // 需要调用的 Agent
>     Confidence float64            // 置信度
>     Reasoning  string             // 推理过程
> }
>
> // Few-shot examples 提升准确率
> const intentPrompt = `
> 你是一个运维助手意图分类器。
>
> 示例：
> Q: "服务A CPU 高怎么办" → {"agents": ["metric", "log"], "reason": "需要查指标和日志"}
> Q: "如何部署到K8s" → {"agents": ["doc"], "reason": "查文档"}
>
> 现在分类：
> Q: "{{.Query}}" → `
> ```
>
> **Agent 之间的通信：**
>
> 我用的是**共享上下文**模式，不是消息队列：
>
> ```go
> type TaskContext struct {
>     UserQuery   string
>     AgentResults map[string]*AgentResult  // 各 Agent 结果
>     SharedMemory []string                   // 共享记忆
>     History     []Message                  // 对话历史
> }
> ```
>
> 这样做的好处：
> - 简单直接，避免引入 Kafka/RabbitMQ 复杂度
> - 适合同进程内的 Agent 协作
> - 后续可扩展成分布式（用 Redis 做上下文共享）"

### Q7: Multi-Agent 如何避免死锁和循环调用？

**面试官心理：** 考察对分布式系统常见问题的理解。

**参考回答：**

> "这是 Multi-Agent 的核心挑战，我在设计时踩过坑。
>
> **死锁场景1：Agent A 等 B，B 等 A**
>
> 比如 Log Agent 需要 Metric Agent 的结果，Metric Agent 又需要 Log Agent 的结果。
>
> **解决方案：禁止 Agent 间直接依赖**
>
> ```go
> // Master 分发任务时做 DAG 检测
> func (m *MasterAgent) dispatch(tasks []Task) error {
>     // 构建依赖图
>     graph := buildDAG(tasks)
>
>     // 检测环
>     if hasCycle(graph) {
>         return ErrCircularDependency
>     }
>
>     // 只允许 Master 收集结果后分发给其他 Agent
>     // Agent 之间不直接通信
> }
> ```
>
> **死锁场景2：Agent 任务卡住，Master 一直等待**
>
> **解决方案：超时机制 + 降级策略**
>
> ```go
> type ExecutionResult struct {
>     Result  interface{}
>     Timeout bool      // 是否超时
>     Error   error
> }
>
> func (m *MasterAgent) executeWithTimeout(
>     ctx context.Context,
>     agent string,
>     task Task,
>     timeout time.Duration,
> ) *ExecutionResult {
>
>     ctx, cancel := context.WithTimeout(ctx, timeout)
>     defer cancel()
>
>     done := make(chan *ExecutionResult, 1)
>
>     go func() {
>         result, err := m.runAgent(ctx, agent, task)
>         done <- &ExecutionResult{Result: result, Error: err}
>     }()
>
>     select {
>     case <-ctx.Done():
>         return &ExecutionResult{Timeout: true, Error: ctx.Err()}
>     case result := <-done:
>         return result
>     }
> }
> ```
>
> **循环调用场景：Agent 不断调用自己**
>
> **解决方案：最大循环次数 + ReAct 反思**
>
> ```go
> const (
>     MaxReactLoops = 10  // 最大反思次数
> )
>
> func (r *ReActAgent) run(ctx context.Context, query string) (string, error) {
>     history := []Thought{}
>
>     for i := 0; i < MaxReactLoops; i++ {
>         thought := r.think(ctx, query, history)
>
>         if thought.ShouldFinish {
>             return thought.FinalAnswer, nil
>         }
>
>         // 执行 Action
>         obs, err := r.act(ctx, thought.Action)
>         if err != nil {
>             // 反思失败原因，换个思路
>             thought = r.reflect(ctx, thought, err)
>         }
>
>         history = append(history, thought)
>     }
>
>     // 超过最大次数，返回当前最佳结果
>     return r.giveUp(history), nil
> }
> ```
>
> **整体降级策略：**
>
> ```go
> func (m *MasterAgent) HandleWithFallback(ctx context.Context, query string) string {
>     // 尝试完整 Multi-Agent
>     result, err := m.Handle(ctx, query)
>     if err == nil {
>         return result
>     }
>
>     // 降级1：单 Agent
>     result, err = m.singleAgentMode(ctx, query)
>     if err == nil {
>         return result
>     }
>
>     // 降级2：纯 RAG
>     return m.pureRAG(query)
> }
> ```
>
> **监控告警：**
>
> ```go
> // 检测异常模式
> if loopCount > 5 {
>     metrics.Alert("Agent循环次数过高", map[string]string{
>         "agent": agentName,
>         "query": query,
>     })
> }
> ```
>
> ---
>
> **总结我的设计原则：**
> 1. **禁止 Agent 间直接依赖** - 所有协调通过 Master
> 2. **超时 + 最大次数** - 防止无限等待
> 3. **降级兜底** - 任何环节失败都有保底方案
> 4. **监控异常** - 及时发现循环调用"

## 四、Function Calling / Tools

### Q8: Function Calling 的工程实现有哪些关键点？

**面试官心理：** 考察工程落地能力，不是调 API 就行。

**参考回答：**

> "Function Calling 看似简单，调个 API 就完了，但要做到生产级有很多细节。
>
> **我的工具系统架构：**
>
> ```
> ┌─────────────────────────────────────────────────────────┐
> │                    Tool System                          │
> ├─────────────────────────────────────────────────────────┤
> │                                                          │
> │   ┌──────────────┐     ┌──────────────┐              │
> │   │    Tool      │     │    Tool      │              │
> │   │   Registry   │────▶│   Executor   │              │
> │   │  (注册中心)   │     │  (执行器)     │              │
> │   └──────────────┘     └──────┬───────┘              │
> │          │                     │                       │
> │          ▼                     ▼                       │
> │   ┌──────────────┐     ┌──────────────┐              │
> │   │   Schema     │     │   Security   │              │
> │   │  Generator   │     │   Checker    │              │
> │   │  (自动生成)   │     │  (安全检查)   │              │
> │   └──────────────┘     └──────────────┘              │
> │                                                          │
> └─────────────────────────────────────────────────────────┘
> ```
>
> **关键点1：工具自动注册**
>
> ```go
> // 用反射 + 注解自动注册
> type Tool struct {
>     Name        string
>     Description string
>     Parameters  map[string]ParamSchema
> }
>
> // 定义工具
> type PrometheusTool struct{}
>
> func (t *PrometheusTool) Name() string {
>     return "prometheus_query"
> }
>
> func (t *PrometheusTool) Description() string {
>     return "查询 Prometheus 指标，支持 CPU、内存、请求量等"
> }
>
> // 注册到全局中心
> func init() {
>     registry.Register(&PrometheusTool{})
> }
> ```
>
> **关键点2：参数校验**
>
> ```go
> type ParameterValidator struct {
>     schemas map[string]*ParamSchema
> }
>
> func (v *ParameterValidator) Validate(params map[string]interface{},
>     schema *ParamSchema) error {
>
>     // 类型检查
>     for name, param := range schema.Properties {
>         value, ok := params[name]
>         if !ok {
>             if param.Required {
>                 return fmt.Errorf("missing required param: %s", name)
>             }
>             continue
>         }
>
>         // 类型校验
>         if !v.checkType(value, param.Type) {
>             return fmt.Errorf("invalid type for %s: got %T, want %s",
>                 name, value, param.Type)
>         }
>
>         // 范围校验
>         if param.Min != nil && v.toFloat(value) < *param.Min {
>             return fmt.Errorf("%s must be >= %v", name, *param.Min)
>         }
>     }
>
>     return nil
> }
> ```
>
> **关键点3：安全兜底（Human-in-the-loop）**
>
> ```go
> func (e *ToolExecutor) Execute(ctx context.Context, call *ToolCall) (*Result, error) {
>     // 1. 安全检查
>     if isDangerous(call) {
>         // 发送确认请求
>         confirmed, err := e.confirmService.Request(ctx, &ConfirmRequest{
>             Tool:     call.Name,
>             Params:   call.Params,
>             Reason:   "检测到危险操作",
>             UserID:   getUserID(ctx),
>         })
>         if err != nil || !confirmed {
>             return nil, ErrOperationNotConfirmed
>         }
>     }
>
>     // 2. 执行
>     return e.execute(ctx, call)
> }
>
> // 危险操作黑名单
> var DangerousPatterns = []string{
>     "rm -rf",
>     "kubectl delete",
>     "DROP TABLE",
>     "shutdown",
> }
>
> func isDangerous(call *ToolCall) bool {
>     for _, pattern := range DangerousPatterns {
>         if strings.Contains(call.String(), pattern) {
>             return true
>         }
>     }
>     return false
> }
> ```
>
> **关键点4：限流保护**
>
> ```go
> type RateLimiter struct {
>     redis *redis.Client
>     limit int
> }
>
> // 令牌桶限流
> func (r *RateLimiter) Allow(toolName string) bool {
>     key := fmt.Sprintf("ratelimit:tool:%s", toolName)
>
>     count, _ := r.redis.Incr(ctx, key).Result()
>     if count == 1 {
>         r.redis.Expire(ctx, key, time.Minute)
>     }
>
>     return count <= int64(r.limit)
> }
> ```
>
> **关键点5：错误重试**
>
> ```go
> func (e *ToolExecutor) executeWithRetry(ctx context.Context,
>     call *ToolCall, maxRetries int) (*Result, error) {
>
>     var lastErr error
>     for i := 0; i < maxRetries; i++ {
>         result, err := e.executeOnce(ctx, call)
>         if err == nil {
>             return result, nil
>         }
>
>         // 非重试错误直接返回
>         if !isRetryable(err) {
>             return nil, err
>         }
>
>         lastErr = err
>         time.Sleep(time.Duration(i+1) * 100 * time.Millisecond)
>     }
>
>     return nil, lastErr
> }
> ```
>
> ---
>
> **总结：Function Calling 生产级的 5 个关键**
>
> 1. **自动注册** - 用反射减少人工维护
> 2. **参数校验** - 类型、范围、必填都要检查
> 3. **安全兜底** - 危险操作必须人工确认
> 4. **限流保护** - 防止刷接口和 LLM 重复调用
> 5. **错误重试** - 网络问题导致的失败可以重试"

## 五、记忆系统

### Q10: Agent 的记忆系统怎么设计？

**面试官心理：** 考察对 Agent 状态管理的理解，不是简单存数据库。

**参考回答：**

> "记忆系统是 Agent 的'大脑'，我设计了三层结构：
>
> ```
> ┌─────────────────────────────────────────────────────────┐
> │                    Memory Architecture                  │
> ├─────────────────────────────────────────────────────────┤
> │                                                          │
> │   ┌─────────────┐                                       │
> │   │   Working   │  ←→  当前对话上下文                    │
> │   │   Memory    │      (内存，毫秒级访问)                │
> │   │  (内存)     │                                       │
> │   └──────┬──────┘                                       │
> │          │                                               │
> │          │ 定期写入                                       │
> │          ▼                                               │
> │   ┌─────────────┐                                       │
> │   │   Short    │  ←→  跨会话上下文                      │
> │   │   Term     │      (Redis，秒级访问)                 │
> │   │  (Redis)   │                                       │
> │   └──────┬──────┘                                       │
> │          │                                               │
> │          │ 定期总结                                       │
> │          ▼                                               │
> │   ┌─────────────┐                                       │
> │   │   Long     │  ←→  重要经验持久化                    │
> │   │   Term     │      (向量库，跨年保留)                │
> │   │  (Vector)  │                                       │
> │   └─────────────┘                                       │
> │                                                          │
> └─────────────────────────────────────────────────────────┘
> ```
>
> **Working Memory（工作记忆）**
>
> ```go
> type WorkingMemory struct {
>     messages []Message
>     maxSize int  // 比如保留最近 10 轮
> }
>
> func (w *WorkingMemory) Add(msg Message) {
>     w.messages = append(w.messages, msg)
>     if len(w.messages) > w.maxSize {
>         w.messages = w.messages[1:]  // 先进先出
>     }
> }
> ```
>
> **Short Term Memory（短期记忆）**
>
> ```go
> type RedisShortTerm struct {
>     client *redis.Client
>     ttl    time.Duration  // 比如 24 小时
> }
>
> func (m *RedisShortTerm) Store(ctx context.Context, sessionID string,
>     events []MemoryEvent) error {
>
>     key := fmt.Sprintf("memory:short:%s", sessionID)
>
>     data, _ := json.Marshal(events)
>     return m.client.Set(ctx, key, data, m.ttl).Err()
> }
>
> func (m *RedisShortTerm) Get(ctx context.Context,
>     sessionID string) ([]MemoryEvent, error) {
>
>     key := fmt.Sprintf("memory:short:%s", sessionID)
>     data, err := m.client.Get(ctx, key).Bytes()
>
>     var events []MemoryEvent
>     json.Unmarshal(data, &events)
>     return events, nil
> }
> ```
>
> **Long Term Memory（长期记忆）**
>
> 核心问题：什么都存会爆炸，只存重要的。
>
> 我的策略是**定期总结**：
>
> ```go
> type LongTermMemory struct {
>     vectorStore *QdrantStore
>     summarizer  *LLMSummarizer
> }
>
> // 定期总结短期记忆
> func (m *LongTermMemory) Consolidate(ctx context.Context,
>     sessionID string) error {
>
>     // 1. 获取短期记忆
>     shortTerm := m.redis.Get(ctx, sessionID)
>
>     // 2. 总结（只保留精华）
>     summary := m.summarizer.Summarize(ctx, &SummaryRequest{
>         Events:   shortTerm,
>         MaxWords: 200,  // 压缩到 200 字
>     })
>
>     // 3. 存入向量库
>     embedding := m.embedder.Embed(ctx, summary.Content)
>
>     return m.vectorStore.Upsert(ctx, &Point{
>         ID:       fmt.Sprintf("%s:%d", sessionID, time.Now().Unix()),
>         Vector:   embedding,
>         Metadata: map[string]interface{}{
>             "content":   summary.Content,
>             "timestamp": time.Now(),
>             "topics":    summary.Topics,
>         },
>     })
> }
> ```
>
> **检索记忆：**
>
> ```go
> func (m *MemorySystem) Recall(ctx context.Context,
>     query string) (*MemoryContext, error) {
>
>     // 1. 检索长期记忆
>     queryEmb := m.embedder.Embed(ctx, query)
>     longTerm := m.vectorStore.Search(ctx, queryEmb, topK=5)
>
>     // 2. 合并短期记忆
>     shortTerm := m.redis.GetRecent(ctx, sessionID, limit=5)
>
>     // 3. 返回上下文
>     return &MemoryContext{
>         LongTermHistory:  longTerm,
>         RecentEvents:     shortTerm,
>     }, nil
> }
> ```
>
> **为什么分层？**
>
> | 层级 | 存储 | 容量 | 保留时间 | 用途 |
> |-----|------|------|---------|------|
> | Working | 内存 | 10 条 | 会话内 | 当前对话上下文 |
> | Short | Redis | 100 条 | 24h | 跨会话连续对话 |
> | Long | 向量库 | 无限 | 永久 | 重要经验复用 |
>
> **和人类记忆的对应：**
>
> - Working Memory = 工作记忆，当前正在想的
> - Short Term = 短期记忆，今天发生的事
> - Long Term = 长期记忆，学到的知识
>
> **踩过的坑：**
>
> 初期我把所有对话都存 Redis，结果：
> 1. Token 消耗爆炸（每次都要塞进 prompt）
> 2. 检索效果差（相关和不相关混在一起）
>
> 改成总结+向量检索后，检索准确率从 45% 提升到 78%。"

### Q12: 讲讲 Go 的并发模型，Agent 调度怎么用好 Goroutine？

**面试官心理：** 深入考察 Go 并发理解。

**参考回答：**

> "Go 的并发模型核心是 **CSP（Communicating Sequential Processes）**，和传统线程不同。
>
> **Go 并发三件套：**
>
> **1. Goroutine - 轻量级执行单元**
>
> ```go
> // 创建一个 goroutine 很简单
> go doSomething()
>
> // 比线程轻量：
> // - 线程：2MB 栈，启动慢，调度依赖 OS
> // - Goroutine：2KB 栈，毫秒级启动，GMP 调度器
>
> // GMP 模型：
> // G (Goroutine) → P (Processor) → M (Machine/Thread)
> // 全局 G 队列 + 本地 P 队列，减少竞争
> ```
>
> **2. Channel - 通信机制**
>
> ```go
> // 无缓冲 channel - 同步通信
> ch := make(chan int)
>
> // 有缓冲 channel - 异步通信
> ch := make(chan int, 10)
>
> // 发送和接收
> ch <- value  // 发送
> v := <-ch    // 接收
>
> // select - 多路复用
> select {
> case msg := <-ch1:
>     handle(msg)
> case msg := <-ch2:
>     handle(msg)
> case <-time.After(5 * time.Second):
>     timeout()
> }
> ```
>
> **3. sync 包 - 同步原语**
>
> ```go
> // WaitGroup - 等待一组任务完成
> var wg sync.WaitGroup
> for _, task := range tasks {
>     wg.Add(1)
>     go func(t Task) {
>         defer wg.Done()
>         execute(t)
>     }(task)
> }
> wg.Wait()  // 阻塞直到所有任务完成
>
> // Mutex - 保护共享资源
> var mu sync.Mutex
> mu.Lock()
> counter++
> mu.Unlock()
>
> // Once - 只执行一次
> var once sync.Once
> once.Do(init)
> ```
>
> **我的 Agent 调度实战：**
>
> ```go
> type Scheduler struct {
>     workers    int           // 最大并发数
>     taskQueue  chan *Task   // 任务队列
>     resultChan chan *Result  // 结果队列
> }
>
> func (s *Scheduler) Start(ctx context.Context) {
>     // 启动固定数量的 worker
>     for i := 0; i < s.workers; i++ {
>         go s.worker(ctx, i)
>     }
>
>     // 分发任务
>     for _, task := range s.getTasks() {
>         s.taskQueue <- task
>     }
> }
>
> func (s *Scheduler) worker(ctx context.Context, id int) {
>     for {
>         select {
>         case <-ctx.Done():
>             return
>         case task := <-s.taskQueue:
>             result := s.executeTask(ctx, task)
>             s.resultChan <- result
>         }
>     }
> }
> ```
>
> **常见并发问题：**
>
> **问题1：goroutine 泄漏**
>
> ```go
> // ❌ 泄漏：没有退出机制
> func leak() {
>     ch := make(chan int)
>     go func() {
>         ch <- 1  // 如果没人读，永远阻塞
>     }()
> }
>
> // ✅ 正确：使用 context 取消
> func noLeak(ctx context.Context) {
>     ch := make(chan int)
>     go func() {
>         select {
>         case ch <- 1:
>         case <-ctx.Done():
>             return  // context 取消时退出
>         }
>     }()
> }
> ```
>
> **问题2：竞争条件**
>
> ```go
> // ❌ 竞争
> var counter int
> go func() { counter++ }()
> go func() { counter++ }()
>
> // ✅ 使用 Mutex
> var mu sync.Mutex
> var counter int
> mu.Lock()
> counter++
> mu.Unlock()
> ```
>
> **问题3：死锁**
>
> ```go
> // ❌ 死锁：两个 channel 互相等待
> ch1 := make(chan int)
> ch2 := make(chan int)
> go func() { <-ch1; ch2 <- 1 }()
> go func() { <-ch2; ch1 <- 1 }()
>
> // ✅ 按固定顺序加锁
> var mu1, mu2 sync.Mutex
> func swap() {
>     // 始终先锁 mu1，再锁 mu2
>     mu1.Lock()
>     mu2.Lock()
>     defer mu2.Unlock()
>     defer mu1.Unlock()
> }
> ```
>
> **我的调度策略：**
>
> ```go
> // 1. 限制并发数 - 防止打爆资源
> semaphore := make(chan struct{}, maxConcurrency)
>
> // 2. 超时控制 - 防止任务卡死
> ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
> defer cancel()
>
> // 3. 错误收集 - 不让一个错误搞崩全部
> var errs []error
> var mu sync.Mutex
>
> for _, task := range tasks {
>     go func(t Task) {
>         defer wg.Done()
>
>         if err := execute(t); err != nil {
>             mu.Lock()
>             errs = append(errs, err)
>             mu.Unlock()
>         }
>     }(task)
> }
>
> wg.Wait()
> if len(errs) > 0 {
>     log.Printf("完成，但有 %d 个错误: %v", len(errs), errs)
> }
> ```"

## 七、系统设计与架构

### Q13: 如果让你设计一个通用的 Agent 框架，你会怎么做？

**面试官心理：** 考察系统设计能力，看你能不能抽象出通用模式。

**参考回答：**

> "这是一个很好的架构设计题，我先说核心设计理念：
>
> **核心理念：插件化 + 可组合**
>
> ```
> ┌─────────────────────────────────────────────────────────┐
> │                   Agent Framework                       │
> ├─────────────────────────────────────────────────────────┤
> │                                                          │
> │   ┌─────────────────────────────────────────────────┐   │
> │   │              Agent Core                          │   │
> │   │  ┌─────────┐ ┌─────────┐ ┌─────────┐          │   │
> │   │  │ Memory  │ │ Planner │ │Executor │          │   │
> │   │  │ Manager │ │         │ │         │          │   │
> │   │  └─────────┘ └─────────┘ └─────────┘          │   │
> │   └─────────────────────────────────────────────────┘   │
> │                        │                                 │
> │                        ▼                                 │
> │   ┌─────────────────────────────────────────────────┐   │
> │   │           Plugin System                          │   │
> │   │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐   │   │
> │   │  │Tools   │ │Retrieval│ │LLM     │ │Storage │   │   │
> │   │  │Plugins │ │Plugins  │ │Plugins │ │Plugins │   │   │
> │   │  └────────┘ └────────┘ └────────┘ └────────┘   │   │
> │   └─────────────────────────────────────────────────┘   │
> │                                                          │
> └─────────────────────────────────────────────────────────┘
> ```
>
> **核心接口定义：**
>
> ```go
> // Agent 接口 - 所有 Agent 都实现这个
> type Agent interface {
>     Name() string
>     Plan(ctx context.Context, task *Task) (*Plan, error)
>     Execute(ctx context.Context, plan *Plan) (*Result, error)
>     Reflect(ctx context.Context, result *Result) error
> }
>
> // Memory 接口
> type Memory interface {
>     Remember(ctx context.Context, event *Event) error
>     Recall(ctx context.Context, query string) ([]*Event, error)
>     Forget(ctx context.Context, criteria *ForgetCriteria) error
> }
>
> // Tool 接口
> type Tool interface {
>     Name() string
>     Description() string
>     Schema() *ToolSchema
>     Execute(ctx context.Context, params map[string]interface{}) (*Result, error)
> }
>
> // LLM 接口（支持多 provider）
> type LLM interface {
>     Generate(ctx context.Context, req *GenerateRequest) (*GenerateResponse, error)
>     Embed(ctx context.Context, text string) ([]float32, error)
>     Name() string
> }
> ```
>
> **框架核心实现：**
>
> ```go
> type AgentFramework struct {
>     llm      LLM
>     memory   Memory
>     tools    map[string]Tool
>     registry *PluginRegistry
>
>     // 策略
>     planningStrategy   PlanningStrategy
>     executionStrategy  ExecutionStrategy
>     reflectionStrategy ReflectionStrategy
> }
>
> // 执行循环
> func (f *AgentFramework) Run(ctx context.Context, task *Task) (*Result, error) {
>     // 1. 规划
>     plan, err := f.planningStrategy.CreatePlan(ctx, task)
>     if err != nil {
>         return nil, err
>     }
>
>     // 2. 记忆检索
>     relevantMemories := f.memory.Recall(ctx, task.Query)
>     plan.Context = append(plan.Context, relevantMemories...)
>
>     // 3. 执行
>     result, err := f.executionStrategy.Execute(ctx, plan, f.tools)
>     if err != nil {
>         // 反思重试
>        反思 := f.reflectionStrategy.Analyze(ctx, err)
>         if 反思.ShouldRetry {
>             plan = f.planningStrategy.ModifyPlan(ctx, plan, 反思)
>             result, err = f.executionStrategy.Execute(ctx, plan, f.tools)
>         }
>     }
>
>     // 4. 记忆保存
>     f.memory.Remember(ctx, &Event{
>         Task:    task,
>         Result:  result,
>         Success: err == nil,
>     })
>
>     return result, err
> }
> ```
>
> **插件系统：**
>
> ```go
> // 插件注册
> type PluginRegistry struct {
>     llms    map[string]LLM
>     tools   map[string]Tool
>     storage map[string]Storage
> }
>
> func (r *PluginRegistry) RegisterLLM(name string, llm LLM) {
>     r.llms[name] = llm
> }
>
> func (r *PluginRegistry) RegisterTool(tool Tool) {
>     r.tools[tool.Name()] = tool
> }
>
> // 使用
> framework := NewAgentFramework(
>     WithLLM("openai", openaiLLM),
>     WithLLM("ollama", ollamaLLM),
>     WithTool(prometheusTool),
>     WithTool(lokiTool),
>     WithMemory(redisMemory),
> )
> ```
>
> **配置驱动：**
>
> ```yaml
> agent:
>   name: "OpsAssistant"
>   llm:
>     provider: "ollama"
>     model: "qwen2.5:7b"
>
>   memory:
>     type: "redis"
>     ttl: 86400
>
>   tools:
>     - name: "prometheus"
>       enabled: true
>     - name: "loki"
>       enabled: true
>
>   strategies:
>     planning: "react"        # react / plan-and-execute
>     execution: "parallel"    # parallel / sequential
>     reflection: "enabled"
> ```
>
> **扩展点设计：**
>
> | 扩展点 | 接口 | 说明 |
> |-------|------|------|
> | LLM Provider | `LLM` | 支持 OpenAI/Ollama/本地模型 |
> | Memory | `Memory` | 支持 Redis/向量库/混合 |
> | Tool | `Tool` | 自定义业务工具 |
> | Planning | `PlanningStrategy` | ReAct/Plan-and-Execute |
> | Execution | `ExecutionStrategy` | 并行/串行/优先级 |
> | Reflection | `ReflectionStrategy` | 反思重试逻辑 |
>
> **使用示例：**
>
> ```go
> // 创建一个运维 Agent
> opsAgent := framework.NewAgent(&AgentConfig{
>     Name: "OpsAgent",
>     LLM: "ollama",
>     Tools: []string{"prometheus", "loki", "k8s", "doc_search"},
>     Memory: "redis",
> })
>
> // 运行
> result, _ := opsAgent.Run(ctx, &Task{
>     Query: "帮我分析订单服务 CPU 飙高的问题",
> })
>
> // 创建一个研发 Agent
> devAgent := framework.NewAgent(&AgentConfig{
>     Name: "DevAgent",
>     LLM: "openai",
>     Tools: []string{"git", "code_search", "doc_search"},
>     Memory: "redis",
> })
> ```
>
> **关键设计原则：**
>
> 1. **接口抽象** - 不要依赖具体实现
> 2. **策略模式** - 不同场景用不同策略
> 3. **插件化** - 新增功能不需要改核心代码
> 4. **可配置** - 所有行为都可通过配置调整"

### Q14: 如何保证 Agent 系统的稳定性和可靠性？

**面试官心理：** 考察工程化能力，生产级系统必备。

**参考回答：**

> "这是从'能用'到'生产级'的关键，我分几个维度说：
>
> **稳定性保障：**
>
> **1. 限流保护**
>
> ```go
> type RateLimiter struct {
>     redis    *redis.Client
>     strategy TokenBucket  // 令牌桶
> }
>
> func (r *RateLimiter) Allow(ctx context.Context, key string) error {
>     if !r.strategy.TryAcquire() {
>         return ErrRateLimitExceeded
>     }
>     return nil
> }
>
> // 针对不同维度限流
> // - 用户维度：防止单用户刷接口
> // - 工具维度：防止 LLM 重复调用同一工具
> // - 全局维度：保护后端服务
> ```
>
> **2. 熔断降级**
>
> ```go
> type CircuitBreaker struct {
>     failures    int
>     threshold   int      // 连续失败多少次
>     timeout     time.Duration  // 熔断多久
>     state       State
> }
>
> func (cb *CircuitBreaker) Call(ctx context.Context,
>     fn func() error) error {
>
>     if cb.state == Open {
>         return ErrCircuitOpen
>     }
>
>     err := fn()
>
>     if err != nil {
>         cb.failures++
>         if cb.failures >= cb.threshold {
>             cb.state = Open
>             go cb.resetAfterTimeout()
>         }
>         return err
>     }
>
>     cb.failures = 0
> cb.state = Closed
>     return nil
> }
> ```
>
> **3. 超时控制**
>
> ```go
> // 每个环节都要有超时
> ctx, cancel := context.WithTimeout(ctx, 120*time.Second)
> defer cancel()
>
> // Agent 执行超时
> agentCtx, agentCancel := context.WithTimeout(ctx, 30*time.Second)
> defer agentCancel()
>
> // 工具执行超时
> toolCtx, toolCancel := context.WithTimeout(ctx, 60*time.Second)
> defer toolCancel()
> ```
>
> **可靠性保障：**
>
> **4. 幂等设计**
>
> ```go
> type IdempotentExecutor struct {
>     redis *redis.Client
>     next  *ToolExecutor
> }
>
> func (e *IdempotentExecutor) Execute(ctx context.Context,
>     call *ToolCall) (*Result, error) {
>
>     // 生成幂等 key
>     key := fmt.Sprintf("idempotent:%s:%v",
>         call.Name, sortedParams(call.Params))
>
>     // 检查是否执行过
>     cached, err := e.redis.Get(ctx, key).Result()
>     if err == nil {
>         return unmarshal(cached)
>     }
>
>     // 执行
>     result, err := e.next.Execute(ctx, call)
>
>     // 缓存结果
>     if err == nil {
>         e.redis.Set(ctx, key, marshal(result), 24*time.Hour)
>     }
>
>     return result, err
> }
> ```
>
> **5. 错误重试**
>
> ```go
> func withRetry(ctx context.Context,
>     maxRetries int,
>     fn func() error) error {
>
>     var lastErr error
>     for i := 0; i < maxRetries; i++ {
>         err := fn()
>         if err == nil {
>             return nil
>         }
>
>         // 非重试错误直接返回
>         if !isRetryable(err) {
>             return err
>         }
>
>         lastErr = err
>
>         // 指数退避
>         select {
>         case <-time.After(time.Duration(1<<i) * 100 * time.Millisecond):
>         case <-ctx.Done():
>             return ctx.Err()
>         }
>     }
>
>     return lastErr
> }
> ```
>
> **监控告警：**
>
> **6. 可观测性**
>
> ```go
> // 结构化日志
> logger.Info("tool execution",
>     zap.String("tool", toolName),
>     zap.Duration("duration", duration),
>     zap.Error(err),
> )
>
> // Prometheus 指标
> metrics.IncCounter("agent_tool_calls_total",
>     "tool", toolName,
>     "status", status,
> )
>
> metrics.ObserveHistogram("agent_tool_duration_seconds",
>     "tool", toolName,
>     value,
> )
>
> // Langfuse 追踪
> trace := langfuse.StartSpan(ctx, "agent_run")
> trace.RecordInput(query)
> trace.RecordOutput(response)
> trace.RecordMetadata("agent_count", len(agents))
> ```
>
> **7. 健康检查**
>
> ```go
> type HealthChecker struct {
>     checks []HealthCheck
> }
>
> func (h *HealthChecker) Register(name string, fn func() error) {
>     h.checks = append(h.checks, HealthCheck{Name: name, Fn: fn})
> }
>
> func (h *HealthChecker) Check() *HealthReport {
>     report := &HealthReport{}
>     for _, check := range h.checks {
>         if err := check.Fn(); err != nil {
>             report.Failures = append(report.Failures, check.Name)
>         }
>     }
>     report.Healthy = len(report.Failures) == 0
>     return report
> }
>
> // 注册健康检查
> health.Register("redis", func() error {
>     return redis.Ping(ctx).Err()
> })
> health.Register("qdrant", func() error {
>     return qdrant.Health(ctx)
> })
> health.Register("ollama", func() error {
>     return ollama.Ping(ctx)
> })
> ```
>
> **降级策略：**
>
> ```go
> func (a *Agent) HandleWithFallback(ctx context.Context,
>     query string) string {
>
>     // 尝试完整流程
>     result, err := a.fullPipeline(ctx, query)
>     if err == nil {
>         return result
>     }
>
>     // 降级1：简化流程
>     result, err = a.simplePipeline(ctx, query)
>     if err == nil {
>         return result
>     }
>
>     // 降级2：纯 RAG
>     result, err = a.pureRAG(ctx, query)
>     if err == nil {
>         return result
>     }
>
>     // 降级3：返回友好错误
>     return "抱歉，我现在无法处理你的请求，请稍后再试"
> }
> ```
>
> ---
>
> **我的稳定性实践清单：**
>
> ```
> □ 限流：Redis 令牌桶，防止刷接口
> □ 熔断：工具调用失败率 > 50% 时熔断
> □ 超时：每个环节都设置合理超时
> □ 重试：指数退避，针对可重试错误重试
> □ 幂等：工具执行结果缓存，支持幂等调用
> □ 日志：结构化日志，记录完整调用链
> □ 指标：Prometheus 指标，QPS/延迟/错误率
> □ 链路：Langfuse 追踪，复现 Agent 思考过程
> □ 健康：/health 端点，检测依赖服务状态
> □ 降级：多级降级策略，保证服务可用
> ```"

## 八、开放性问题

### Q15: 你认为当前 Agent 技术的局限性是什么？

**面试官心理：** 考察思考深度，不只是会用，还要能批判性思考。

**参考回答：**

> "这是个好问题，我会坦诚说：
>
> **1. 规划能力有限**
>
> 现在的 Agent 在简单任务上表现不错，但复杂任务容易'迷路'。
>
> 比如用户说'帮我分析为什么这个月收入下降了'，Agent 可能：
> - 查到收入数据
> - 查到订单量下降
> - 查到流量下降
> - 但不知道要继续查'为什么流量下降'
>
> 缺少**多跳推理**和**主动探索**能力。
>
> **2. 可靠性不稳定**
>
> - LLM 的不确定性导致同样问题可能不同答案
> - Function Calling 仍有概率乱调用
> - 复杂任务的成功率远低于简单任务
>
> **3. 记忆系统不成熟**
>
> - 短期记忆：上下文窗口有限，长对话效果差
> - 长期记忆：如何决定什么是'重要'的很难
> - 记忆检索：相关性判断不准确
>
> **4. 评估困难**
>
> - 没有像传统软件那样的'正确答案'
> - 评估成本高（需要人工标注）
> - 难以自动化测试
>
> **5. 成本和延迟**
>
> - LLM 推理成本高
> - 多 Agent 多次调用成本爆炸
> - 延迟影响用户体验
>
> ---
>
> **我认为的突破方向：**
>
> 1. **垂直领域微调** - 通用模型 + 领域微调，效果更好
> 2. **更好的规划算法** - 借鉴强化学习，让 Agent 更会规划
> 3. **多模态融合** - 不仅仅处理文本，还能处理图表、界面
> 4. **工具生态** - 更丰富的工具支持，更强的执行力
> 5. **评估体系** - 建立行业标准的 Agent 评测基准
>
> 我的项目 GopherSentinel 也是在尝试解决其中一些问题，
> 比如用 Multi-Agent 弥补单 Agent 能力不足，
> 用 Rerank 提高检索可靠性，
> 但我也清楚这些方案都有局限性。"

### Q16: 未来 Agent 的发展趋势是什么？

**面试官心理：** 考察对技术趋势的关注和思考。

**参考回答：**

> "我比较关注几个方向：
>
> **1. Agent 专用模型**
>
> 现在用通用 LLM 做 Agent，未来会有专门为 Agent 优化的模型：
> - 更强的工具调用能力
> - 更长的规划步数
> - 内置的安全机制
>
> Anthropic 的 Claude 3.5、OpenAI 的 GPT-4o 已经在这方面探索。
>
> **2. Multi-Agent 协作深化**
>
> 不只是 Master-Worker，会有更复杂的 Agent 社会：
> - Agent 之间协商分工
> - Agent 互相评估和监督
> - 涌现出群体智能
>
> **3. 长期记忆突破**
>
> 当前记忆系统很粗糙，未来可能：
> - 更智能的记忆总结
> - 记忆可以'遗忘'和'强化'
> - 跨 Agent 共享记忆
>
> **4. 安全与可控性**
>
> 这是企业落地的关键：
> - 更细粒度的权限控制
> - 可审计的操作记录
> - 防止 Prompt 注入
> - Human-in-the-loop 成为标配
>
> **5. 行业垂直 Agent**
>
> 通用 Agent 效果一般，垂直领域 Agent 会更流行：
> - 研发 Agent（代码、测试、部署）
> - 运维 Agent（监控、排障、容量规划）
> - 客服 Agent（对话、推荐、情感分析）
>
> **我的判断：**
>
> 未来 1-2 年，Agent 技术会在**特定垂直场景**取得突破，
> 而不是通用 AGI。
>
> GopherSentinel 定位在运维场景，就是这个判断的实践。"
