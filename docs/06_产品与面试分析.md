### 2.2 必讲的 5 个核心亮点

#### 亮点 1：RAG 系统设计（深度）

```go
// ❌ 初级实现（大部分人会这样写）
func Query(question string) string {
    embedding := embed(question)
    docs := vectorDB.Search(embedding, topK=5)
    return llm.Generate(question, docs)
}

// ✅ 高级实现（面试要展示的）
func (r *RAGChain) Query(ctx context.Context, req *QueryRequest) (*QueryResponse, error) {
    // 1. 查询改写 - 扩展同义词，提升召回
    rewrittenQuery := r.queryRewriter.Rewrite(ctx, req.Query)
    
    // 2. 混合检索 - 向量 + BM25 融合
    vectorResults := r.vectorSearch.Search(rewrittenQuery)
    bm25Results := r.bm25Search.Search(rewrittenQuery)
    fusedResults := r.hybridFusion.Fuse(vectorResults, bm25Results)
    
    // 3. Rerank - 精排提升相关性
    rerankedResults := r.reranker.Rerank(rewrittenQuery, fusedResults)
    
    // 4. 上下文压缩 - 减少 token 浪费
    compressedContext := r.contextCompressor.Compress(rerankedResults)
    
    // 5. 生成 + 引用追踪
    response, err := r.llm.Generate(ctx, compressedContext)
    response.Citations = extractCitations(rerankedResults)
    
    return response, nil
}
```

**面试话术：**
> "我实现的 RAG 链路有 5 个关键优化点：
> 1. 查询改写 - 解决用户问题表述模糊的问题
> 2. 混合检索 - 向量检索擅长语义相似，BM25 擅长关键词匹配，两者互补
> 3. Rerank - 使用 BGE-Reranker 做二阶段精排，把最相关的文档排在前面
> 4. 上下文压缩 - 用 LLMLingua 压缩 prompt，减少 token 消耗
> 5. 引用追踪 - 生成结果时标注参考来源，方便用户溯源"

#### 亮点 2：Multi-Agent 协作（架构）

```go
// Agent 调度器核心逻辑
func (s *Scheduler) Schedule(ctx context.Context, task *Task) (*Result, error) {
    // 1. 意图识别 - 判断需要哪些 Agent
    intent := s.recognizer.Recognize(ctx, task.Query)
    
    // 2. 并行分发 - 利用 Go 并发优势
    var wg sync.WaitGroup
    results := make(chan *AgentResult, len(intent.RequiredAgents))
    
    for _, agentType := range intent.RequiredAgents {
        wg.Add(1)
        go func(agent Agent) {
            defer wg.Done()
            // 带超时的 Agent 执行
            result, _ := s.executeWithTimeout(ctx, agent, task, 30*time.Second)
            results <- result
        }(s.getAgent(agentType))
    }
    
    // 3. 等待完成 + 结果聚合
    wg.Wait()
    close(results)
    
    aggregated := s.aggregator.Aggregate(ctx, collectResults(results))
    
    // 4. 反思优化 - ReAct 循环
    if intent.NeedReflection {
        return s.reActLoop(ctx, task, aggregated)
    }
    
    return aggregated, nil
}
```

**面试话术：**
> "Multi-Agent 的设计参考了 Map-Reduce 思想：
> - Map 阶段：Master Agent 识别意图后，并行调度 Log/Metric/Doc Agent
> - Reduce 阶段：聚合各 Agent 结果，综合分析
> 
> 关键技术点：
> 1. Goroutine 并发 - 比 Python 的 asyncio 性能更高
> 2. 超时控制 - 防止某个 Agent 卡死导致整体挂掉
> 3. ReAct 反思 - 如果结果不满意，自动重试优化"

#### 亮点 3：Function Calling 工程化（细节）

```go
// 工具注册中心 - 支持动态注册
type ToolRegistry struct {
    mu    sync.RWMutex
    tools map[string]Tool
    
    // 运行时工具定义（LLM 可感知）
    schema map[string]*ToolSchema
}

// 工具执行器 - 带安全和限流
func (e *ToolExecutor) Execute(ctx context.Context, call *ToolCall) (*ToolResult, error) {
    // 1. 参数校验
    if err := e.validator.Validate(call); err != nil {
        return nil, err
    }
    
    // 2. 危险操作检查
    if e.isDangerous(call) {
        // Human-in-the-loop: 发送确认请求
        confirmed, err := e.confirmService.Request(ctx, call)
        if err != nil || !confirmed {
            return nil, ErrOperationNotConfirmed
        }
    }
    
    // 3. 限流检查
    if !e.rateLimiter.Allow(call.ToolName) {
        return nil, ErrRateLimitExceeded
    }
    
    // 4. 执行 + 超时
    return e.executeWithTimeout(ctx, call, 60*time.Second)
}

// 工具定义示例（LLM 理解的方式）
type ToolSchema struct {
    Name        string                 `json:"name"`
    Description string                 `json:"description"`
    Parameters  map[string]ParamSchema `json:"parameters"`
    Examples    []ToolExample          `json:"examples,omitempty"`
}
```

**面试话术：**
> "Function Calling 的工程化有 3 个关键设计：
> 1. 工具注册中心 - 用反射机制自动扫描，所有工具自动注册
> 2. 安全兜底 - 危险操作必须人工确认，防止 AI 误删数据
> 3. 限流保护 - 防止用户恶意刷接口，也防止 LLM 重复调用

> 这个设计让新增工具变得非常简单：
> 只需要实现 Tool 接口，添加 @Tool 注解，工具就自动注册到 LLM 的 tool list 中"

#### 亮点 4：记忆系统（工程完整度）

```go
// 分层记忆架构
type MemorySystem struct {
    // 工作记忆 - 当前会话
    working *WorkingMemory
    
    // 短期记忆 - Redis
    shortTerm *RedisMemory
    
    // 长期记忆 - 向量数据库
    longTerm *VectorMemory
    
    // 记忆总结器
    summarizer *Summarizer
}

// 记忆写入流程
func (m *MemorySystem) Remember(ctx context.Context, event *MemoryEvent) error {
    // 1. 先写入工作记忆
    m.working.Store(event)
    
    // 2. 异步写入短期记忆
    go func() {
        m.shortTerm.Append(ctx, event)
        
        // 3. 定期总结写入长期记忆
        if m.shouldSummarize() {
            summary := m.summarizer.Summarize(ctx, m.shortTerm.GetRecent(10))
            m.longTerm.Store(ctx, summary)
        }
    }()
    
    return nil
}

// 记忆检索流程
func (m *MemorySystem) Recall(ctx context.Context, query string) (*MemoryContext, error) {
    // 1. 检索长期记忆
    longTermResults := m.longTerm.Search(ctx, query)
    
    // 2. 合并短期记忆
    shortTermResults := m.shortTerm.GetRecent(5)
    
    // 3. 返回上下文
    return &MemoryContext{
        LongTerm:  longTermResults,
        ShortTerm: shortTermResults,
    }, nil
}
```

**面试话术：**
> "记忆系统参考了人类认知的三层记忆模型：
> 1. 工作记忆 - 内存中，当前对话快速访问
> 2. 短期记忆 - Redis，跨会话保留
> 3. 长期记忆 - 向量库，重要经验持久化

> 关键设计：定期总结机制 - 避免向量库膨胀，又不丢失重要经验"

```go
// Langfuse 追踪 Agent 思维链
func (a *Agent) Run(ctx context.Context, input string) (string, error) {
    // 创建追踪 span
    trace, ctx := a.tracer.StartSpan(ctx, "agent_run",
        langfuse.WithMetadata(map[string]string{
            "agent_type": a.Name,
        }),
    )
    defer trace.End()
    
    // 记录每个思考步骤
    thought1 := a.think(ctx, "理解用户意图")
    trace.Log(thought1)
    
    thought2 := a.think(ctx, "规划执行步骤")
    trace.Log(thought2)
    
    // 记录工具调用
    if toolCall := a.decideTool(ctx); toolCall != nil {
        trace.RecordToolCall(toolCall.Name, toolCall.Params)
        
        result := a.executeTool(ctx, toolCall)
        trace.RecordToolResult(result)
    }
    
    response := a.generateResponse(ctx)
    
    // 记录最终输出
    trace.RecordOutput(response)
    trace.Score(float64(a.evaluateQuality(response)))
    
    return response, nil
}
```

> 2. 结构化日志记录每次工具调用
> 3. 埋点采集 Token 消耗，监控 LLM 成本

> 这样线上出了问题，可以精确回放 AI 的思考过程，快速定位是 RAG 召回问题还是 LLM 生成问题"

### 4.1 自我介绍模板

> "我叫 xxx，有 X 年 Go 后端开发经验。
> 
> 最近半年我在做一个 AI 智能运维助手的项目，叫 GopherSentinel。
> 
> 核心解决的是微服务场景下，运维和研发人员排查问题效率低的问题。
> 
> 技术上我实现了三个创新点：
> 1. **混合 RAG** - 结合向量检索和 BM25，用 Rerank 做二阶段精排，召回准确率提升到 85%+
> 2. **Multi-Agent 架构** - Master-Worker 模型，用 Goroutine 并发调度日志、指标、文档三个 Agent
> 3. **Function Calling** - 把内部系统 API 自动注册成 LLM 可调用的工具
> 
> 项目已经完成了基础功能，接下来计划接入 Langfuse 做可观测性优化。"

### 4.2 项目深挖应对

**Q: 为什么用 Go 不用 Python？**

> "Python 确实生态更丰富，但这个项目有几个场景 Go 更适合：
> 1. **高并发 Agent 调度** - 运维场景经常需要同时查询多个系统，Go 的 Goroutine 比 Python asyncio 更轻量
> 2. **工具集成** - 项目需要集成 K8s SDK、Prometheus Client，这些 Go 客户端更成熟
> 3. **部署简单** - 编译成单一二进制，比 Python 环境依赖问题少很多
> 4. **性能敏感** - RAG 链路中大量 JSON 序列化和向量计算，Go 的性能优势明显

**Q: RAG 效果怎么评估的？**

> "我构建了 100 条标注测试集，覆盖了：
> - 事实性问答 (能否正确回答文档内容)
> - 推理问答 (需要综合多段文档推理)
> - 边界情况 (文档中没有明确答案时能否如实说不知道)
> 
> 评估指标用了 RAGAS 框架的 Faithfulness 和 Answer Relevance
> 当前 Faithfulness 得分是 0.87，还有提升空间，主要是长文本分块策略需要优化"

**Q: 遇到的最大挑战是什么？**

> "最大的挑战是意图识别的准确率。
> 初期 Agent 分发经常出错，比如用户问'这个接口能不能删'，系统会误判为需要调用日志 Agent。
> 
> 我做了几轮优化：
> 1. 收集了 500 条真实用户 query，标注正确的 Agent 分类
> 2. 用 few-shot prompting 优化 Master Agent 的分类 prompt
> 3. 增加了置信度阈值，低于 0.7 时返回多个 Agent 结果让 LLM 自行选择
> 
> 最终意图识别准确率从 65% 提升到了 89%"
